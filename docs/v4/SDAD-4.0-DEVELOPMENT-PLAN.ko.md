# SDAD 4.0 — 의도·해석·진행·정정 중심 개발 계획

상태: 현재 사용자 지시로 채택된 새 4.0 제품 방향과 개발 계획. 상세 정보 계약·구현·검증·릴리스는 단계별로 진행한다. 이 문서의 채택은 제품 구현 완료나 배포 승인이 아니다.

진입점: [SDAD 4.0 현재 기준](README.md). 이번 대화에서 만든 의도·해석·진행·정정 계획을 4.0으로 정의한다. 이전 4.0 Blueprint, RFC, 엔지니어링 검토와 관련 연구안은 폐기했으며 현재 요구사항이나 기본 의존성으로 사용하지 않는다.

## 1. 총평과 제품 목표

SDAD 3.2.2는 현재 의도, 작업 경계, 검증 근거, 미해결 문제, 사용자 권한과 연속성을 보존하는 기반으로 적합하다. 다음 개선은 이 정보를 사용자가 직접 연결하고 감시해야 하는 부담을 줄이는 데 집중한다.

Companion의 제품 목표는 다음과 같다.

> 사용자가 자신의 요청을 AI가 어떻게 이해하고 실행하는지 확인하고, 필요한 부분을 바로잡고, 그 정정이 실제 결과에 반영됐는지 확인할 수 있게 한다.

핵심 사용자 여정은 `요청 → AI의 해석 → 요청별 진행 → 사용자 정정 → 수신 확인 → 반영 결과 → 사용자 수락`이다. 명확하게 승인된 작업은 매번 확인 버튼을 기다리지 않고 진행한다.

성공은 사용자 재설명, 상태 확인, 결정 추적, 재개와 재작업 부담을 줄이면서 기능 품질·권한 준수·누락 방지를 유지하는 것으로 정의한다. 실행 시간과 토큰도 함께 측정한다.

## 4. 역할과 데이터 책임

| 역할 | 책임 | 책임의 한계 |
| --- | --- | --- |
| 사용자 | 목표·우선순위·중요한 제품 선택·보호 행동·결과 수락 결정 | packet ID, 문서 경로와 상태 정합성을 매번 직접 관리할 필요 없음 |
| 작업 AI | 해석·가정·주요 선택 보고, 구현·검증, 정정 수신과 반영 보고, 변경된 기록 갱신 | 자신의 보고만으로 사용자 승인이나 실제 검증을 생성할 수 없음 |
| SDAD | 현재 의도·권한·작업·근거·연속성의 저장 위치와 의미 정의 | 에이전트 실행·중지를 기술적으로 보장하지 않음 |
| Inspector | 기존 기록을 읽고 관계·출처·최신성·불확실성을 표시, 정정 요청 작성 보조 | 문서 존재·Git 변경·단계 표식으로 AI 의도나 완료를 추측하지 않음 |
| 선택적 연결 어댑터 | 특정 대상에 요청 전달, 실제 수신·실행 상태 관측 | 전송 성공을 의미 반영·중지·사용자 수락으로 바꾸지 않음 |

기존 Python Inspector Core, ProtocolAdapter, React/TypeScript UI, Markdown viewer, 출처 패널을 재사용한다. 기존 레이아웃 전체를 교체하거나 일반 프로젝트 관리 서비스를 만들지 않는다.

## 5. 화면과 핵심 인터랙션

### 5.1 기본 정보 구조

현재 3단 구조를 유지한다. 왼쪽은 요청·작업 탐색, 가운데는 선택한 요청의 해석·진행·결정, 오른쪽은 근거와 변경 영향을 제공한다. 모든 기존 문서 탐색 기능을 한 번에 개편하지 않고 중심 작업 화면부터 개선한다.

| 화면 영역 | 표시 내용 | 사용자 행동 |
| --- | --- | --- |
| 내 요청과 AI의 이해 | 원문/출처, 이해한 목표, 포함·제외 범위, 주요 가정, 미확인 사항 | 해석 수정, 범위 조정, 근거 보기 |
| 요청별 진행 | 각 수락 기준에 대한 구현 보고, 검증 근거, 남은 필수 작업 | 결과·검사 보기, 누락 지적 |
| 중요한 선택 | 관련 요구, 선택·대안·근거, 영향, 변경 이력 | 설명 확인, 변경 요청 |
| 내 결정이 필요한 일 | 선택 사항, 추천·대안, 영향, 해당 대기 범위 | 구체적 선택, 보류, 요청 수정 |
| 출처와 최신성 | 원본 경로/앵커/리비전, 보고 주체, 마지막 보고·관측 시점 | 원문 열기, 최신 기록 확인 |

Plan/Route/Implement/Verify/Report는 보조 위치 표시다. TODO 수나 단계 위치를 제품 완성률로 표시하지 않는다. 현재 '판단 이유'가 단계 표식에 관한 설명이면 '단계 표시 근거'로 이름을 정확히 바꾼다. 제품 선택의 이유는 작업 AI가 명시한 보고에서 읽는다.

### 5.2 요청과 해석

예시 요청: '설정을 저장해서 다시 들어와도 유지되게 해줘.'

예시 AI 해석: '같은 브라우저 재접속 시 설정 복원. 계정·기기 간 동기화는 이번 범위에 포함하지 않음.'

- 사용자 원문과 AI 해석은 다른 정보로 보존한다.
- 기본적으로 모든 해석에 '승인'을 요구하지 않는다. 실행 권한은 실제 사용자 요청과 기존 유효 권한에서 확인한다.
- 제품 결과를 크게 바꾸는 모호성이 남으면 그 선택을 사용자에게 묻는다. 독립 작업은 진행 가능 범위를 명시한다.
- AI가 보고하지 않은 해석은 '미보고'다. Inspector가 생성한 요약이 필요해지면 별도 표시하며 권위 있는 요구사항으로 승격하지 않는다. 최초 MVP는 추론형 요약에 의존하지 않는다.

### 5.3 정정과 영향 확인

사용자가 '같은 계정이면 다른 기기에서도 유지되어야 해'라고 정정하면 다음을 비교한다.

| 비교 항목 | 기존 | 정정 후 |
| --- | --- | --- |
| 동작 범위 | 현재 브라우저 | 같은 계정의 여러 기기 |
| 필요한 구현 | 로컬 저장 | 계정별 서버 저장·복원 |
| 필요한 확인 | 새로고침·재접속 | 다른 기기·다른 계정·저장 실패 |
| 기존 결과 | 현재 브라우저 동작 근거 | 해당 범위에서 유지 가능, 새 요구의 근거로는 불충분 |

영향이 자동으로 분석되지 않았으면 '영향 분석 대기'로 표시한다. 근거 없이 재사용 가능 파일이나 구현 기간을 확정하지 않는다. 정정된 요구에 영향을 받는 주장만 재검증 대상으로 표시하고, 관련 없는 검증 이력까지 폐기하지 않는다.

### 5.4 정정 요청의 상태

다음은 Companion 상호작용 상태다. `active_packet.status`에 추가하지 않는다.

`초안 → 복사됨 또는 전달됨 → 수신 확인 → 변경 계획 보고 → 반영 보고 → 검증 근거 확인`

- 복사됨은 전달됨이 아니다. 전송 성공은 수신 확인이나 반영 완료가 아니다.
- 연결이 없는 경우 미확인 상태를 유지한다. 일정 시간이 지났다는 이유로 성공 처리하지 않는다.
- AI의 수신 확인에는 요청 ID·대상 작업·이해한 변경·기준 요구 리비전·영향 범위를 포함한다.
- 오래된 요청에 대한 응답은 현재 정정의 응답으로 표시하지 않는다.
- 반복 전달은 같은 요청 ID로 취급한다. 새 정정은 새 ID와 이전 요청에 대한 supersedes 관계로 구분한다.
- 원래 요청에 영향을 받는 작업의 정지·재계획 여부는 AI의 응답이나 실제 관측에서 확인한다.
- 중지 기능을 추가할 때 '중지 요청 전달', '에이전트 중지 보고', '프로세스 중지 관측'을 구분한다. 문서 기반 요청만으로 프로세스 종료를 보장하지 않는다.

### 5.5 사용자 결정과 수락

- 해석 정정, 범위 변경, 보호 행동 승인, 결과 수락은 서로 다른 행동이다.
- '확인' 하나로 모든 의미를 처리하지 않는다. 버튼은 허용할 행동을 구체적으로 표현한다.
- 추천·대안·영향·결정이 필요한 이유를 함께 제공한다.
- 사용자의 침묵이나 화면 조회는 승인·수락이 아니다. 이미 명확한 권한이 있는 작업의 계속 진행과 구분한다.
- 사용자 수락은 요청한 결과와 해당 근거의 리비전에 연결한다. 요청을 수정하면 영향받는 수락 범위를 다시 검토한다.
- 최초 MVP는 검토와 요청문 작성에 집중한다. Inspector가 직접 승인·수락 기록을 쓰는 기능은 후속 쓰기 계약 대상으로 남긴다.

## 6. 4.0 정보 계약과 3.2.2 출발점

### 6.1 기존 권위 재사용

| 정보 | 기존 저장 위치/근거 | Companion의 역할 |
| --- | --- | --- |
| 수락된 요구·범위 | 활성 SPEC, 실제 사용자 지시의 출처 | 관련 절과 리비전 표시 |
| AI의 현재 작업 해석 | 현재 TODO의 작업 선언과 필요한 구현 노트 | 'AI 보고'로 표시. 사용자 의도와 구분 |
| 결정·근거·영향 | 구현 노트 또는 ADR | 관련 요구·결과 링크 표시 |
| 미완료·보류 | TODO/findings | 원래 요청 전체의 남은 기준과 연결 |
| 관찰된 검사·한계 | 실제 검증 결과와 기존 evidence 기록 | 검사 선언과 실행 결과를 구분 |
| 현재 실행·인수인계 | state/current_handoff | 현재 포인터와 복원 근거 표시 |
| 사용자 승인·수락 | 프로젝트가 선택한 기존 권위 있는 결정 기록 | 출처와 적용 범위 참조 |
| 아직 전달하지 않은 정정 | Inspector의 로컬 초안 | 프로젝트 권위가 아닌 요청 초안 |

새로운 통합 장부를 권위로 만들지 않는다. 첫 4.0 MVP는 기존 3.2.2 기록 위에 최소 메타데이터와 링크를 제공하는 방식으로 개발한다. 원문 전체·상태·결정을 여러 곳에 복제하지 않는다. 스키마 변경이 필요한 경우 W2에서 필요성·호환성·전환 비용을 명시적으로 검토한다. 버전 이름만으로 마이그레이션을 요구하지 않는다.

### 6.2 선택적 보고 규약

W2에서 표준 예제와 파서 계약을 확정한다. 후보 필드는 기록 ID, 종류, 대상 packet/요구, 작성 주체, 기준 리비전, 출처, supersedes/응답 대상, 짧은 내용, 근거 포인터다. 모든 기록에 모든 필드를 강제하지 않고 종류별 필수값을 정한다.

- 첫 MVP의 기준은 SDAD state v2와 기존 Doctor 보고 스키마의 유지다. 4.0이라는 제품 방향을 이유로 state version을 4로 바꾸지 않는다.
- 신규 읽기 프로젝션은 Inspector가 독립적으로 버전 관리한다. 기존 snapshot 2에 무문서 필드를 덧붙이지 않는다. 호환성 정책과 소비자 테스트를 먼저 정의한다.
- 파싱되지 않는 기존 문서는 원문 열기를 유지한다. 구조화된 해석/결정 표시는 '지원하지 않음/미보고'로 남긴다.
- 전용 AI 실행기 없이 Markdown을 읽고 쓰는 에이전트도 참여할 수 있게 한다.
- 보고는 작업 시작·중요한 해석 변경·정정 수신·주요 선택·검증 결과·실제 인수인계 시 갱신한다. 매 도구 호출마다 보고하지 않는다.
- 보고한 시점과 파일을 관측한 시점을 구분한다. 둘 중 어느 것도 사실의 정확성을 단독으로 보장하지 않는다.
- 상충하는 현재 기록을 시간·ID 크기로 임의 선택하지 않는다. 충돌을 표시하고 명시적인 조정을 기다린다.

## 7. 기존 작업의 재사용과 경계

| 현재 자산 | 재사용 | 추가 작업 |
| --- | --- | --- |
| 공식 SDAD 3.2.2 adapter/state/INDEX | 그대로 비교 기준 유지 | 자연어 요청·중단 범위·상태 안내의 의미 충돌 수정 후보 |
| 미커밋 coordination/decision-trace profile | 기존 3.x 작업으로 보존 | 이전 4.0 유래라는 이유로 승계하지 않고 W2에서 채택/수정/제외 판단 |
| SI-020 DevelopmentFlow | 3단 구조, 단계 레일, 원문 열기, 다국어 기반 | 요청 중심 정보 순서와 해석·결정 표시 |
| bounded Markdown viewer | 읽기 한계와 경로 경계 유지 | 선택적 보고 블록의 파싱·위치 연결 |
| ProtocolAdapter와 Inspector Core | Doctor 정규화, 조회·갱신 경로 | 선택적 보고 프로젝션과 최신성/충돌 처리 |
| 기존 테스트·호환 fixture | 기존 동작 회귀 확인 | 실제 정정 왕복·실패·오래된 응답 시나리오 |

구현 착수 시 두 저장소의 dirty diff를 먼저 목록화하고 후보 기준을 고정한다. 격리 작업 공간에 필요한 변경만 선택적으로 가져온다. 기존 사용자 변경의 전체 채택·덮어쓰기를 가정하지 않는다. 이 계획을 작성한 행위는 기존 변경의 수락이 아니다.

## 8. 개발 작업 묶음과 순서

표의 ID는 계획 내부 식별자다. 활성 packet이나 기존 SI 번호를 할당한 것이 아니다. 모든 단계에서 변경 코드와 실제 실행 결과를 구분해 보고한다.

| 단계 | 범위·산출물 | 의존성 | 완료 기준 |
| --- | --- | --- | --- |
| W0 기준 고정과 흐름 검증 | 이전 4.0 폐기, 새 방향 정립, 양쪽 저장소 후보 diff, 핵심 사용자 여정과 테스트 fixture | 없음 | 공개 기준·보존된 로컬 후보·새 4.0 제안을 구분하고 재사용 대상 확정 |
| W1 4.0 실행 규칙 정리 | 3.2.2를 기준으로 질문형 요청, 검증 실패, 중단 범위, 보고 용어/상태 대응 개선 | W0 | 허용/중단 예제와 새 어댑터·문서·기존 스키마의 일치 |
| W2 최소 상호작용 계약 | 기존 문서의 선택적 보고 형식, 요청·응답 연결, 최신성·충돌, Inspector 프로젝션 버전 | W0, W1의 의미 결정 | 손으로 작성한 유효/무효 fixture와 기존 프로젝트 fallback 통과 |
| W3 읽기 중심 화면 | 요청/해석, 요구별 진행, 중요 결정, 필요한 사용자 선택, 출처 | W2 | 기존 UI를 유지하며 원문/AI 보고/관측/검증/미확인을 구분 |
| W4 정정 왕복 MVP | 해석 수정, 영향 비교, 요청문 복사, 응답과 반영 근거 연결 | W3 | 전용 연결기 없이 같은 요청을 정정하고 올바른 응답·결과를 확인 |
| W5 사용자 평가와 단순화 | 현행 UI와 MVP의 과제별 비교, 오류 수정, 기록 부담 평가 | W4 | 사용자 판단 정확도·통제·연속성 유지 및 개선 근거 확보 |
| W6 선택적 직접 연결 | 한 환경에서 요청 전달·수신 확인, 재연결·중복·잘못된 대상 처리 | W5 및 실제 연결 수단 검증 | 요청 오발송·오래된 응답 오인 없이 전송과 반영을 분리 |
| W7 배포 후보 | 통합 검증, 지원 플랫폼별 패키지 스모크, 마이그레이션/릴리스 문서 | 수락된 W5 또는 W6 후보 | 정확한 후보 산출물·검증 범위·남은 제한과 사용자 결정 연결 |

권장 마일스톤은 M1=W0~W2(계약 검토 가능), M2=W3~W4(첫 사용자 체험), M3=W5(가치 검증), M4=선택적 W6와 W7(제품 전달)이다. W7은 직접 연결 없이 읽기/복사 MVP만으로도 구성할 수 있다.

W3의 합성 fixture 기반 UI 설계는 W2 초안을 바탕으로 준비할 수 있지만, 실제 파서와 통합은 계약 확정 뒤 진행한다. 별도 에이전트 병렬 개발을 기본 전제로 하지 않는다.

고정 일수는 아직 제시하지 않는다. W0에서 기존 미커밋 작업의 재사용량, 지원 OS와 평가 참여 가능성을 확인한 뒤 마일스톤별 실행 예산을 산정한다. 연결 API의 접근 가능성이 확인되지 않은 W6를 확정 일정에 포함하지 않는다.

## 9. 작업별 구현 경계

### W1: 4.0 프로토콜

- canonical `templates/project-control-files/AGENTS.md`에서 의미를 수정하고 renderer로 어댑터를 동기화한다.
- `docs/implicit-rules.md`, 작업·위험·인수인계 playbook과 일치시킨다.
- `review-findings.md`의 'production-readiness evidence가 없으면 feature work 중단' 문구를 영향받는 행동·주장의 차단으로 좁힌다.
- 기존 상태 값은 유지한다. `evidence-ready`를 근거 없이 `software_verified`로 자동 변환하지 않는다.
- packet 분할 완화는 즉시 전면 적용하지 않는다. 같은 목표·수락 기준·권한의 내부 단위가 불필요한 전환을 만드는지 W5에서 평가한다.
- 정식 v3.2.2 태그는 그대로 둔다. 이번 작업의 제품·프로토콜 방향은 4.0이며 구현 후보와 공개 릴리스는 구분한다. 구체적인 사전 릴리스·제품 버전과 호환성 표시는 W7에서 정한다. 3.2.x에 별도 백포트할지는 이 계획의 필수 범위가 아니다.

### W2~W4: Inspector

- `web/src/components/DevelopmentFlow.tsx`, 관련 타입·문구·테스트와 Python 읽기 프로젝션을 확장한다.
- 단계 표시 근거와 AI 작업 판단을 구분한다. 다음 단계라는 이유로 'AI가 다음에 하겠다고 선언한 행동'으로 표시하지 않는다.
- 네 언어, 테마, 기존 UI 배율·반응형, 원문·출처 탐색을 보존한다.
- 최초 MVP는 검사 대상 저장소를 수정하지 않는다. 초안 저장이 필요하면 기존 앱 소유 데이터 영역을 사용하고 프로젝트·대상 요청별로 구분한다.
- 요청문에 대상 프로젝트/작업, 변경 전 해석, 정정, 알고 있는 영향, 요청 ID·기준 리비전·응답 요청을 포함한다. 숨은 범위 확대 문구를 넣지 않는다.
- 복사 이후 실제 전달은 사용자와 기존 에이전트 환경을 통해 수행한다. 실제 사용자 지시를 받은 AI가 기존 권위 파일을 갱신하고 수신·반영을 보고한다.
- 프로파일이 없거나 보고가 멈춰도 기존 Inspector 조회 기능은 동작한다.

### W6: 직접 연결

- 실제 공개/허용된 연결 수단이 있는 환경 하나에서 시작한다. 현재 Codex 앱 안의 도구가 외부 Inspector에서 사용 가능하다고 가정하지 않는다.
- 자동 채팅 기록 채굴을 핵심 경로로 삼지 않는다. 사용자가 선택한 대상과 명시적으로 보고된 정보를 사용한다.
- 전송 대상·권한·재시도·중복 제거·재연결·실패 상태를 검증한다. 저장소 문서의 지시만으로 전송 대상을 바꾸지 않는다.
- 범용 프로젝트 쓰기, 자동 승인·수락·배포, 일반 에이전트 스케줄러는 포함하지 않는다.
- 앱에서 직접 승인/수락 기록을 쓰거나 실행을 제어하는 기능은 별도 권한·연동 계약을 확정한 후 작업 범위를 명시한다.

## 10. 검증 계획

### 10.1 필수 시나리오

| 시나리오 | 통과 조건 |
| --- | --- |
| 명확한 작은 요청 | 불필요한 승인 대기 없이 실행, 확인 가능한 해석과 결과 제공 |
| 질문형 수정 부탁/정보 질문 | 두 의도를 구분하고 분석 요청을 구현 권한으로 바꾸지 않음 |
| 구현 도중 의도 정정 | 새 요청과 응답이 연결되고, 영향받는 옛 작업·주장을 분리 |
| 연속된 두 정정과 늦은 응답 | 이전 응답이 최신 요청을 충족한 것으로 표시되지 않음 |
| 보고 누락·읽기 실패·충돌 | 미보고/미확인/충돌 표시, 성공 추정 없음 |
| 검증 명령만 존재 | 실행됨·검증됨으로 표시하지 않음 |
| 필수 하위 작업 보류 | 현재 작업이 끝나도 원래 요청의 미완료 항목이 보임 |
| 서로 다른 프로젝트 전환 | 요청·초안·응답·증거가 이전 프로젝트에서 섞이지 않음 |
| 새 세션에서 재개 | 현재 목표·수정 의도·제약·미해결 문제 복원 가능 |
| 복사/전송/중지 기능 | 복사·전송을 수신·반영·중지 완료로 오인하지 않음 |
| 구형/프로파일 없는 프로젝트 | 기존 읽기 기능 유지, 신규 정보는 명확한 미지원 상태 |
| 작은 화면·다국어 | 주요 행동·근거·미확인 상태가 잘리거나 의미가 바뀌지 않음 |

### 10.2 코드·계약 검사

프로토콜 후보: `python scripts/validate_repo.py`, `python scripts/render_agent_surfaces.py --check`, 영향받는 계약 테스트, 통합 시 전체 unittest와 `git diff --check`.

Inspector 후보: `npm --prefix web test -- --run`, typecheck, build, Python unittest, browser/public repository/SDAD compatibility 계약 검사, 프로젝트 no-write와 파서 경계 검사. 저장소의 적합한 Python 환경을 사용한다.

새 상태를 그려주는 테스트만으로 사용자 해석의 정확성을 주장하지 않는다. 기능 테스트와 별도로 '잘못된 해석을 발견하고 정정해서 반영 확인까지 끝내는' 실제 흐름을 검증한다. 패키지는 배포 후보에서 정확한 산출물로 다시 검사한다.

### 10.3 사용자 가치 평가

비교 조건은 A=정식 3.2.2+현행 Inspector 흐름, B=해석·정정·요구별 결과 MVP다. 가능하면 프로토콜 문구 변경만 적용한 조건도 분리해 UI 효과와 규칙 효과를 구분한다.

- 같은 과제 유형, 같은 모델/도구 설정, 고정된 테스트와 권한 경계를 사용한다.
- 익숙함 효과를 줄이기 위해 동등 과제의 순서를 교차 배치한다. 소규모 사용자 평가와 모델 비교 결과를 섞어 일반 성능으로 주장하지 않는다.
- 사용자 재설명 횟수, 추가 진행 질문, 의도 불일치 발견 시간, 정정 후 올바른 반영 확인 시간, 결정 근거 탐색 시간, 새 세션 복원 오류를 기록한다.
- 완료/미완료/검증 여부/필요한 결정에 대한 사용자 판단 정확도를 측정한다.
- 실행 시간, 사용자 대기·검토 시간, 도구 호출, 입력/캐시 입력/출력 토큰, 제어 문서 수정량도 기록한다.
- 중요한 권한·출처·정정 연결·미완료 누락 실패는 해당 후보 수정을 요구한다. 과제에서 실패가 없었다는 결과를 일반적인 무실패 보장으로 바꾸지 않는다.
- W0에서 과제·평가자·관측 구간·판정 기준을 먼저 정한다. 작은 표본은 탐색적 결과로 보고하며, 개선이 불명확하면 기능을 확장하지 않고 반복 기록·표시를 줄여 재평가한다.

## 11. 범위에서 제외하거나 후속으로 남길 것

- 폐기한 이전 4.0의 상태 엔진·그래프·중앙 스케줄러·실시간 다중 에이전트 관제를 필수 전제로 삼는 작업.
- AI의 내부 추론 수집. 필요한 것은 명시적으로 보고한 해석·선택·근거·불확실성이다.
- 모든 작업의 시작·단계 전환을 확인 버튼으로 승인받는 구조.
- 문서·Git·Doctor 결과만으로 작업의 인과관계, 완료율, 사용자 승인 추정.
- 필수 신규 DB·클라우드 서비스·공급자 SDK와 새로운 프로젝트 권위 장부.
- 현재 공개 배포물에 로컬 SI-019/020 변경이 들어 있다고 가정하는 작업.

## 12. 현재 착수 기준

새 4.0의 첫 구현 목표는 W0~W4다. '요청 하나의 AI 해석을 확인하고, 잘못된 범위를 정정하고, 그 정정과 연결된 응답·검증 결과를 확인한다'가 사용자 체험의 종료 조건이다. 현재 W0~W4는 격리된 로컬 구현 후보에서 소프트웨어 검증을 마쳤다. 현재 결과와 제한은 [진입점](README.md)에 기록했다. 추가 개발 지시에 따라 W5 준비로 초안 연속성과 저장 충돌을 보완하고 [평가 실행 키트](EVALUATION-KIT.ko.md)를 만들었다. W5의 실제 참여자 관측, W6 직접 연결, W7 패키지·릴리스는 아직 남아 있다.

첫 구현에서는 이 계획을 각 저장소의 활성 SPEC/작업 경계에 필요한 만큼 반영했다. 새 파일 전체를 상시 프롬프트로 로드하지 않는다. 이후 사용자의 개발 착수 지시에 따라 첫 W0~W4 MVP를 구현했다. 기존 승인·보존된 변경·새 작업을 구분하고 보호 행동과 릴리스의 권한은 각각 확인한다.
