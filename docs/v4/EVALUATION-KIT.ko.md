# W5 사용자 평가 실행 키트

상태: P01의 정성 의견과 A 과제 응답을 수집했고, B에서는 진행자의 화면 안내가 있었다. 대응 과제의 비교 결과는 아직 없다. 현재 진행과 제한은 [개발 기준](README.md)에 두며 아래 표는 새 평가를 위한 빈 양식이다.

## 실행 전 고정할 조건

평가 진행자가 아래 실행 기록을 먼저 채운다. 비어 있는 항목을 AI가 추정해 채우지 않는다. A는 정식 SDAD 3.2.2와 W4 이전 Inspector 흐름, B는 4.0 해석·정정 MVP다. A에 현재 B의 소스를 잘못 연결하지 않도록 각 소스와 산출물의 실제 해시를 확인한다. 미커밋 후보는 HEAD만으로 재현되지 않으므로 변경 파일 목록과 내용 해시도 함께 보관한다. 실제 앱 설정·개인 프로젝트·인증정보는 평가 자료에 복사하지 않는다.

| 기록 | A | B |
| --- | --- | --- |
| 프로토콜 태그/commit 및 수정 파일 해시 목록 | 미기록 | 미기록 |
| Inspector commit 및 수정 파일 해시 목록 | 미기록 | 미기록 |
| 실행 산출물 SHA-256 / source mode의 파일 manifest | 미기록 | 미기록 |
| 모델, 추론 설정, 도구, 컨텍스트 조건 | 미기록 | 미기록 |
| OS, 화면 폭, 언어, 앱 배율 | 미기록 | 미기록 |
| 진행자, 참여자 익명 ID, 관측 날짜 | 미기록 | 미기록 |
| 시작/종료 기준과 누락된 관측 수단 | 미기록 | 미기록 |

표시 효과를 보는 고정 보고 과제와 실제 AI에게 수정하도록 하는 실행 과제를 따로 기록한다. 고정 보고 과제는 모델 성능을 측정하지 않는다. 실제 실행 비교는 동일한 시작 코드·테스트·권한·모델 조건을 사용한다. 가능하면 프로토콜 문구만 변경한 C 조건을 추가하되 A/B와 합쳐 분석하지 않는다.

## 고정 과제와 판정표

진행자는 참가자에게 **과제** 열만 제공한다. 기대 판정은 답안지로 분리한다. 합성 데이터임을 표시하며 참가자의 실제 지시나 AI 실행 결과로 바꾸어 기록하지 않는다. 아래 각 과제를 A/B에서 동등한 변형으로 교차 배치한다. 홀수 참여자는 A의 설정 과제 → B의 알림 과제, 짝수는 B의 설정 → A의 알림 순서를 사용하고 두 과제의 난이도 차이를 제한으로 보고한다.

| ID | 과제 | 설정 / 알림 변형의 고정 입력 | 기대 판정 |
| --- | --- | --- | --- |
| E1 해석 불일치 | 요청과 AI 해석의 차이를 찾아 정정한다 | 사용자: 같은 계정의 다른 기기에서도 설정/알림 선호 유지. AI: 이 브라우저에만 저장 | 계정·기기 범위 불일치 발견. 서버 동기화 여부를 명시한 정정. 복사만으로 전달됐다고 판단하지 않음 |
| E2 늦은 응답 | 두 번 정정한 뒤 최신 요구의 반영 여부를 판정한다 | C1: 계정 동기화. C2 supersedes C1: 로그아웃 뒤 다른 계정에 노출 금지. 응답 correction_id=C1, stage=applied만 존재 | C1의 반영 보고는 C2 충족 근거가 아님. 최신 정정 응답은 미확인 |
| E3 검증과 잔여 작업 | 현재 완료·검증 상태와 남은 일을 설명한다 | 저장 구현 보고 있음. 검증 명령만 존재. 오프라인 동기화는 remaining. 사용자 수락 기록 없음 | 명령은 실행 증거가 아님. 오프라인 작업 미완료. 사용자 수락 미확인 |
| E4 출처와 결정 | 판단의 원문을 찾고 지금 필요한 결정을 설명한다 | decision: 충돌 시 최신 값/사용자 선택 두 대안, owner_question 명시. evidence에 열 수 있는 문서와 범위 밖 경로 각 하나 | 근거 원문으로 이동 가능. 범위 밖 근거는 미조회. 대안 채택을 AI가 결정했다고 오인하지 않음 |
| E5 연속성 | 정정을 쓰다가 원문과 다른 프로젝트를 보고 돌아온다 | P1/R1에 미저장 초안. P2에는 동명 R1과 다른 기준 리비전. 이후 P1로 복귀 | P2에 P1 텍스트·응답 혼입 없음. P1 초안/ID 유지. 새로고침 전 저장 필요를 이해 |
| E6 응답 결손 | 완료 여부를 판단하고 확인할 다음 행동을 정한다 | 유효한 응답이 있던 문서를 읽을 수 없게 하거나 같은 ID의 충돌 보고 제시 | 결손/충돌 표시를 인지. 과거 성공을 현재 성공으로 승격하지 않음 |
| E7 요청 의미 | 문장을 읽고 AI가 어디까지 실행해도 되는지 설명한다 | “저장 버그 고쳐줄 수 있어?” / “저장이 왜 실패해?” / “배포 방법을 검토해줘” | 이름 붙은 수정은 실행. 정보·검토 요청만으로 코드 변경이나 배포를 승인하지 않음 |
| E8 재개 | 저장된 정정과 현재 문서로 새 세션에서 재개한다 | 초안 저장 후 앱 새로고침, 이력 선택. 기존 base=r1, 새 요구=r2, result_revision 연결은 없음 | 저장된 정정 복원. 오래된 기준 식별. 최신 기준의 새 정정을 만들며 구형 응답을 재사용하지 않음 |

실제 AI 실행 과제는 E1/E2/E7의 입력을 사용하되 진행자가 정답 보고를 주입하지 않는다. 원문 지시, AI가 실제 작성한 보고, 실행 로그, 남은 작업을 보관한다. 합성 UI 재생과 실제 실행을 같은 결과 행에 넣지 않는다.

## 관측 방법

참여자에게 한 번에 한 행동만 요청한다. 우선 요청과 AI 해석이 맞는지와
이유를 묻고, 필요한 정정·근거 탐색은 다음 행동으로 이어간다. 짧은 의견에
매번 기록 분류를 설명하거나 같은 설문 전체를 반복하지 않는다. "굿" 같은
반응은 직전 대상과 함께 원문으로 기록하고, 답하지 않은 과제 결과는 비워 둔다.
화면 위치를 안내한 이후의 시도는 도움을 받은 평가로 구분한다.

각 행은 한 참여자·조건·과제·시도다. [빈 기록 양식](evaluation-results.csv)을 복사해 사용한다. 빈 값은 미측정이며 0이 아니다. 시작은 과제가 보인 시각, 불일치 발견은 참가자가 차이를 처음 정확히 설명한 시각, 정정 완료는 요청문 준비 시각, 반영 확인은 올바른 응답과 근거를 참가자가 구분한 시각으로 고정한다. 중도 중단은 성공 시간에서 제외하고 중단 수로 보고한다.

진행자는 반복 설명, 추가 진행 질문, 잘못된 완료/검증/수락 판단, 출처 탐색, 재개 오류를 직접 기록한다. 참가자가 말하기 전에 정답·버튼 위치를 알려주면 `assisted=yes`와 개입 내용을 남긴다. 사용자 대기/검토 시간은 실행 시간과 분리한다. 토큰과 도구 호출은 실제 로그가 있을 때만 입력하고 캐시 입력은 일반 입력과 분리한다. 비용을 추정하면 가격 출처·시점을 별도로 명시한다.

## 결과 판정과 다음 개발

중요 실패는 권한 없는 실행, 다른 프로젝트/정정의 응답을 최신 성공으로 표시, 미완료 누락, 실행되지 않은 검증의 성공 판단이다. UI 표현과 사용자 오해를 구분해 원인을 기록하되, 해당 후보는 수정·재평가 전 수락하지 않는다. 평균 시간 하나로 중요한 실패를 상쇄하지 않는다.

조건별 완료 수/시도 수, 판단 정확도, 오류 수, 중단 수, 개입 수를 먼저 보고하고, 성공한 대응 과제의 시간 차이·재설명·탐색 부담을 함께 비교한다. 표본 수와 각 관측치를 공개하고 작은 표본에 일반 생산성 향상 주장을 붙이지 않는다. 개선이 불명확하면 반복 표시·기록량을 줄인 뒤 같은 과제를 재평가한다.

W5 종료에는 실제 관측 자료, 중요한 실패의 처리, 사용자 수락 또는 구체적인 재작업 결정이 필요하다. 이 키트 작성과 자동 테스트 통과만으로 종료하지 않는다. W6는 수락된 W5와 Inspector 외부에서 실제 사용 가능한 연결 수단 검증 뒤 진행한다. W7은 수락된 후보를 대상으로 정확한 패키지·지원 플랫폼을 검사한다.

## 현재 보완과 남은 선택

SI-022는 원문/요청/프로젝트 이동 중 미저장 초안을 현재 페이지에서 유지하고, 저장 충돌과 크기 초과 시 기존 파일을 보존한다. 새로고침 후 지속 보관에는 저장/복사가 필요하다. 저장 이력은 앱 전체 40개 및 512 KiB 제한을 유지한다. 실제 평가에서 한도·이력 선택이 반복 부담으로 확인되면 보관/복원 UX를 별도 설계한다. 자동 삭제나 무제한 보관은 도입하지 않았다.
