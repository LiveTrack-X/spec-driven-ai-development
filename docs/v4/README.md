# SDAD 4.0 — 현재 개발 기준

상태: W0~W4 첫 MVP를 격리된 로컬 소스 후보로 구현·소프트웨어 검증했다. W5를 위한 초안 연속성 보완과 평가 준비를 추가했다. 실제 사용자 평가와 공개 릴리스는 아직 수행하지 않았다.

## 현재 결정

사용자가 이번 대화에서 만든 개발 방향을 **SDAD 4.0**으로 정의하고 이전 4.0 설계를 삭제하도록 지시했다. 이에 따라 현재 4.0의 개발 계획은 [의도·해석·진행·정정 중심 개발 계획](SDAD-4.0-DEVELOPMENT-PLAN.ko.md) 하나로 통합한다.

> 사용자가 자신의 요청을 AI가 어떻게 이해하고 실행하는지 확인하고, 바로잡고, 그 정정이 실제 결과에 반영됐는지 확인할 수 있게 한다.

핵심 여정은 **요청 → AI의 해석 → 요청별 진행 → 사용자 정정 → 수신 확인 → 반영 결과 → 사용자 수락**이다. 첫 MVP는 해석 확인부터 정정과 반영 확인까지 한 흐름을 완성한다.

## 기준과 범위

- 출발점은 정식 SDAD 3.2.2와 현재 Inspector다. 기존 통제·증거·결정·연속성의 가치를 유지한다.
- 3.2.2 태그와 공개 버전 표시는 보존한다. 이 폴더를 만들었다고 제품이 4.0으로 출시된 것은 아니다.
- state v2와 기존 Doctor 계약을 첫 MVP의 기준으로 사용한다. 4.0이라는 이름 때문에 스키마 번호나 마이그레이션을 강제로 바꾸지 않는다.
- 현재 Inspector의 읽기 전용 경계를 유지하는 해석·진행 표시와 정정 요청 복사부터 개발한다. 직접 전달과 제어는 후속 연결 계약으로 분리한다.
- 자동 승인·배포, 필수 다중 에이전트 관제, 별도 그래프 엔진은 첫 MVP의 전제가 아니다.
- 사용자 재설명·판단·정정·재개 부담을 기능 품질·권한 준수·실행 비용과 함께 평가한다.

## 이전 4.0 정리

기존 Blueprint, Semantic Model RFC, Companion Multi-Agent Coordination RFC, Decision Trace Review RFC, Engineering Review, Related Work Research의 6개 문서를 삭제했다. 이전의 3.x 비호환, 별도 Core와 필수 다중 에이전트 구조는 새 4.0 요구사항으로 승계하지 않는다. 다른 작업이나 과거 대화에 남아 있는 이전 설계는 현재 권위를 갖지 않는다.

기존 3.x 검증기·renderer 보완과 Inspector UI 변경은 독립 작업으로 보존한다. 옛 설계에서 파생된 coordination backport 기록도 3.x 구현 이력으로 남기되 새 4.0의 설계 근거로 자동 채택하지 않는다. 재사용 여부는 W0/W2에서 현재 목표에 맞춰 판단한다.

## 진행 순서

| 단계 | 목표 | 현재 상태 |
| --- | --- | --- |
| W0 | 기준 고정, 기존 변경 분류, 핵심 여정·fixture 확정 | 완료: 기준과 재사용 후보 분리 |
| W1 | 실행 규칙의 해석 충돌 정리 | 문구·어댑터·검증 정합 확인 |
| W2 | 해석·정정·응답·근거의 최소 정보 계약 | 구현·소프트웨어 검증 |
| W3 | 요청 중심 읽기 화면 | 구현·소프트웨어 검증 |
| W4 | 정정 왕복 MVP | 수동 전달 흐름 구현·브라우저 확인 |
| W5 | 사용자 부담·정확성 평가와 단순화 | A 응답·B 정성 의견 수집, 진입·항목 정정 개선 검증, 안내 후 B 과제 판단 대기 |
| W6 | 선택적 직접 연결 | 미착수, 연결 수단 검증 후 |
| W7 | 배포 후보 검증과 전달 | 미착수 |

단계별 범위·의존성·완료 기준은 개발 계획에 둔다. 이 표는 개발 계획의 위치 안내이며 실제 프로젝트의 `sdad-state.yaml`이나 결과 수락 기록을 대체하지 않는다.
