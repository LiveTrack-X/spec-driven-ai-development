# SDAD 핵심 규칙 개선과 실제 실행 기록

상태: 2026-09-13 로컬 후보 개선과 실제 AI 8회 실행 완료. 공개 릴리스·사용자 수락과는 별개다.

## 이번에 바꾼 것

- 구현 전에 요청한 결과·보존 조건과 계획을 대조한다. 명확한 불일치는
  현재 권한 안에서 바로잡고, 해결되지 않은 중요한 선택만 질문한다.
- 핸드오프가 없으면 state → INDEX → 현재 SPEC·소스·테스트·작업 기록으로
  재개한다. 명시적으로 취소된 작업은 이 경로로 자동 재개하지 않는다.
- 완료 보고는 요구별 결과·실제 검사·남은 한계를 연결한다. 테스트 개수만으로
  전체 요구 충족을 선언하지 않으며, 별도 필수 장부를 추가하지 않는다.
- 정정 시 영향받은 요구·계획·TODO·근거를 먼저 맞춘다. 관련 구현과 검증을
  수행하고, 영향받지 않은 작업과 여전히 유효한 근거는 보존한다.
- 실행에서 발견한 상태값 혼동을 막기 위해 state 작성 위치에 허용값을
  표시했다. 설명용 `evidence-ready`와 기계 상태값을 구분한다.
- 발견 사항의 정확한 기록 형식을 템플릿에 표시하고, 관리 파일 변경 후
  사용 가능한 Doctor를 실행하도록 절차를 보완했다. Doctor를 실행하지
  못했으면 수동 확인의 범위와 미실행 사실을 남긴다.

기존 state v2 스키마와 권한·수락 경계는 유지했다. 시작 커널은 압축하고
상세 절차는 기존 playbook에 배치했다. 전역 설치나 공개 릴리스는 하지 않았다.

## 실제 실행 방법

수정 전 로컬 후보와 1차 개선 후보를 각각 동결했다. 두 개의 합성 Python
저장소에서 구현 → 새 세션의 요구 정정 → 새 세션의 설명 요청을 실행했다.
총 6회이며 모두 `gpt-6-astra`, reasoning `high`, Codex CLI
`0.154.0-alpha.6.2`를 사용했다. 기존 npm CLI `0.132.0`의 모델 지원 실패는
실행 준비 실패로 보존하고 행동 평가에서 제외했다.

예제는 기존 설정에 patch를 얕게 병합하는 함수다. 다음 조건을 의도적으로 넣었다.

- 핸드오프 없음, 요구와 충돌하는 임시 TODO 계획.
- 기존 확장 키·중첩 값 보존, 입력 객체 불변, 같은 입력의 같은 결과.
- 실제 외부 요청을 전혀 하지 않고 종료 코드 3을 반환하는 동기화 검사.
- 다음 세션에서 최상위 `None`을 값 저장에서 키 삭제 의미로 정정.
- 마지막에는 설명만 요청하고 파일 변경과 작업 재개를 명시적으로 제외.

AI가 작성한 테스트와 별도로, 작업 저장소 밖에 둔 독립 검사기를 실행했다.
초기 구현은 5개 사례, 정정 구현은 7개 사례를 검사한다. 검사기 자체도
원래 버그·입력 변경·옛 의미 재사용·함수 누락을 거부하는 5개 테스트로 확인했다.

auth 파일만 임시 실행 홈에 복사하고 전역 config·skills·memories·MCP 연결을
제외했다. 임시 인증 홈은 종료 후 삭제했다. 실행 로그·명령·최종 답변·파일
해시·각 단계 스냅샷을 보존했다. 저장소 경계는 지시로 제한한 것이며 별도 OS
격리가 아니므로, 실행 후 명령과 변경 파일도 확인했다.

## 1차 비교 결과

| 확인 항목 | 수정 전 로컬 후보 | 1차 개선 후보 |
| --- | --- | --- |
| 첫 구현의 독립 코드 검사 | 5/5 | 5/5 |
| 정정 후 독립 코드 검사 | 7/7 | 7/7 |
| AI가 실제 실행한 최종 단위 테스트 | 7개 → 11개 | 8개 → 13개 |
| 충돌 계획 수정·핸드오프 없이 진행 | 확인 | 확인 |
| 외부 동기화 미검증 구분 | 확인 | 확인 |
| 설명 요청의 파일 변경 | 0개 | 0개 |
| 불필요한 사용자 답변 대기 | 없음 | 없음 |
| 코드 구현 후 state 검증 | 잘못된 상태값 발생 | 잘못된 상태값 발생 |

두 조건 모두 `evidence_ready`라는 지원하지 않는 상태값을 작성했다.
수정 전 후보는 `authorization_ref` 등의 사용자 정의 packet 필드도 추가했다.
**따라서 코드 검사 통과를 SDAD 전체 실행 성공으로 집계하지 않는다.**

초기 fixture에는 필수 TODO 절 하나가 누락되어 있었고, 구현 기록 경로도
중복 배치되어 있었다. 초기 Doctor 결과는 오류 0·경고 1이었다. 이 두 가지는
평가 도구 작성 결함이며 AI나 SDAD의 실패로 돌리지 않는다. 새로 생성된
잘못된 상태값은 초기 fixture에 없었으며 두 조건의 실제 실행 결과다.

개선 후보는 정정된 요구와 근거를 더 구체적으로 연결했다. 그러나 이 작은
예제에서는 기존 후보도 코드와 권한 경계를 지켰으므로 정확도 우위를 입증하지
못했다. 개선 후보의 TODO는 구현 후 51줄에서 정정 후 114줄로 늘었다.
한 정정 실행에서는 읽기 명령 출력이 665줄로 시작 커널의 500줄 읽기 한도를
넘었다. 지시를 적는 것과 실제로 지키게 하는 것은 별개의 문제다.

| 실제 측정값 | 수정 전 후보 | 1차 개선 후보 |
| --- | ---: | ---: |
| 구현 시간 | 140.162초 | 157.642초 |
| 정정 시간 | 146.735초 | 218.161초 |
| 설명 시간 | 45.145초 | 61.270초 |
| 구현 명령 수 | 15 | 13 |
| 정정 명령 수 | 8 | 15 |

각 조건 한 번이며 일부 독립 실행 시간은 겹쳤다. 캐시·호스트 부하·생성
편차를 통제한 성능 실험이 아니다. 이 숫자는 해당 실행 비용의 관측값이며
일반적인 속도 저하나 생산성 향상 추정치가 아니다. 정확한 CLI 사용량은
로컬 `audit.json`과 각 `result.json`에 있으며 누적 입력에는 캐시가 포함된다.

## 발견 후 보완과 재검증

상태값 안내·기록 간소화·관리 파일 검사 절차를 보완한 뒤 별도 예제를 만들었다.
초기 fixture 결함을 정리하고 strict Doctor 오류 0·경고 0부터 다시 시작했다.
이 단계는 원인별 통제 비교가 아닌 재현된 결함의 표적 재검증이다.

첫 재실행에서 코드 5/5는 통과했고, 지원하지 않는 상태값도 사라졌다.
그러나 발견 사항 ID를 packet 표시보다 앞에 써서 기록 형식 경고가 1개 남았다.
정확한 기록 예시와 저장소 내부의 실제 Doctor 실행 명령을 제공한 뒤
정정을 재실행했다. AI는 새 단위 테스트의 실패를 재현하고 코드를 수정했으며,
실제 Doctor의 경고를 읽고 잘못된 발견 사항 기록도 바로잡았다.

- 최종 AI 단위 테스트: 9개 통과.
- 별도 독립 코드 검사: 7/7 통과.
- AI가 실행한 strict Doctor: 오류 0·경고 0. 평가 측의 별도 재검사도 동일.
- Doctor 런타임·지침·무관 파일의 해시 유지.
- 이전 테스트 결과와 정정 후 결과 구분, 외부 동기화는 계속 미검증으로 보고.

잘못된 기록은 평가 도구가 미리 고치지 않고 보존했다. 이 확인은 지침과
검사기 제공을 함께 바꿨으므로 문구 변경만의 효과로 해석하지 않는다.

프로토콜 전체 회귀는 480개 중 477개 통과·3개 환경상 제외다. 마지막 테스트
모듈 경로 정리 후 관련 69개를 별도로 재검사했다. 저장소 검증, 6개 어댑터
생성 일치, diff 공백 검사도 통과했다. 원래 작업 폴더와 미완료 W5 사용자
평가 기록을 보존했으며 전역 설치·커밋·발행은 수행하지 않았다.

## 남은 장기 문제와 우선순위

1. **정확한 형식의 규칙은 실행 가능한 검사와 함께 배포해야 한다.**
   상태값 안내만으로 첫 오류는 없어졌지만 장부 형식 오류는 남았다.
   프로젝트 적용 시 실제 Doctor 경로를 검증 절차에 연결하는 것이 우선이다.
2. **문서 유지 비용을 따로 측정해야 한다.** 요구별 추적은 유용하지만 작은
   코드 수정을 긴 계획·이력으로 반복 기록하면 재개 때 읽기 비용이 누적된다.
   이번에 짧은 요구 → 검사 → 한계와 기존 근거 링크를 재사용하도록 보완했다.
   수십 회 정정·세션 압축·여러 사람의 작업에서의 효과는 아직 검증하지 않았다.
3. **시작 규칙의 여유가 거의 없다.** 가장 큰 Cursor 표면은 5,996/6,000자다.
   새 규칙을 계속 추가하기보다 반복·중복 규칙을 줄이고 필요한 세부 절차만
   찾아 읽도록 해야 한다. 시작 예산 제한은 이번에도 유지했다.
4. **검증이 표어에 의존하면 문장을 다듬기 어렵다.** `progressive`라는 단어
   존재 검사는 실제 부분 선택·전체 읽기 금지의 계약 검사로 바꿨다.
   기계 상태값과 기록 문법은 여전히 정확하게 검사해야 한다.
5. **실행 도구와 평가 fixture도 노후화된다.** 모델 지원 여부와 strict Doctor
   시작 상태를 먼저 확인하고 실패를 결과에서 숨기지 않아야 한다.
   이번 실행기의 호환 실패와 fixture 결함은 원시 기록에 남겼다.

장기간 신뢰성, 다른 모델의 행동, 실제 제품 개발 생산성, 여러 작업자의 동시
수정은 이 단일 예제만으로 판정할 수 없다. 다음 현장 검증은 규칙 수를 늘리는
것보다 요구 누락·상태 오류·관리 문서 증가·재검증 비용을 함께 추적하는 데 둔다.

## 근거 위치

로컬 원시 근거 폴더는 `SDAD-core-pilot-20260913`이다. `protocol.json`,
`preflight-resolution.md`, `baseline-*-manifest.json`, `candidate-*-manifest.json`,
`runs/*/{raw.jsonl,result.json,commands.json,doctor.json,snapshot/}`와
`followup/`에 조건·실행·정정 이력이 있다. `run_pilot.py`, `test_oracle.py`,
`inspect_doctor.py`도 함께 보존했다. 이 하네스는 현재 PC의 경로를 사용하는
로컬 실험 도구이며 범용 배포 도구로 검증한 것이 아니다.
